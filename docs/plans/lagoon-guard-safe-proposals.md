# Automatic Safe proposals for Lagoon guard redeploys

## Goal

After `lagoon-deploy-vault --guard-only` deploys a replacement guard, the deployer signs and submits the Safe module migration to the Safe Transaction Service. Safe owners still review and execute it. Apply this to both the single-chain and strategy-file multichain deployment paths. A simulated deployment must never submit a live proposal.

## Existing behaviour

- `tradeexecutor/cli/commands/lagoon_deploy_vault.py` already builds guard migration instructions for each Safe: `disableModule(SENTINEL_MODULES, old_guard)` followed by `enableModule(new_guard)`. It writes them into single-chain `Guard migration` and multichain `deployments[slug].guard_migration` artefacts, but only logs the calls.
- The current builder requires exactly one enabled module. Keep that restriction until a migration implementation can locate the old module's actual predecessor in the Safe's linked list.
- `tradeexecutor/cli/commands/lagoon_manual_settle.py` uses `eth_defi.safe.tx.propose_safe_transaction()` and constructs a Safe UI link. `scripts/gmx-ai/propose-cowswap-cleanup.py` shows a MultiSendCallOnly proposal, nonce and pending-proposal checks, and the Transaction Service API key used for reliable production submission.
- The strategy-file path can redeploy guards on multiple chains. Each chain has its own Safe nonce and Transaction Service network despite a shared Safe address.

## Implementation plan

1. **Prepare and validate before deployment.** For a real guard-only redeploy, read the existing Safe on every target chain. Verify its version, that exactly one module is enabled, and that the module matches the old guard when its address was supplied. Check that `PRIVATE_KEY` resolves to a current Safe owner, that the chain's Transaction Service is supported, and that MultiSendCallOnly is deployed. The Service API key is optional. Refuse to deploy if these prerequisites fail. Preserve an explicit `--manual-safe-migration` path for chains without a hosted Transaction Service; it emits the manual migration instructions without promising a submitted proposal. During `--simulate`, do not require Transaction Service access and do not submit; continue to report the manual migration calls as a simulation.
2. **Build one atomic migration per chain.** Use the deployed guard address and a fresh read of enabled Safe modules after deployment. Reject a change to the expected old module. Encode `disableModule(SENTINEL_MODULES, old_guard)` and `enableModule(new_guard)` against that same Safe, each with zero value and Call operation. Wrap them in an ordered MultiSendCallOnly batch, proposed to the Safe with DelegateCall. This avoids an executable intermediate state with no guard enabled. Do not use two independently executable Safe proposals.
3. **Submit and record the proposal.** Use the on-chain `Safe.nonce()` as the candidate nonce and query the Transaction Service for pending transactions at that nonce; do not skip ahead to a later nonce. Build and sign the transaction with the deployer's `PRIVATE_KEY`. Accept an identical hash on retry; reject a different pending transaction without replacing it. Use `eth_defi.safe.tx.propose_safe_transaction()` only if it supports the required MultiSend operation, explicit nonce and production API key; otherwise add the smallest shared submission wrapper around the existing `safe-eth` Transaction Service client. Return the chain-specific Safe transaction hash, nonce, and Safe UI link. Record batch target, operation, calldata or decoded calls, nonce, hash, URL and submission status under a distinct `safe_proposal` field alongside the existing migration instructions. Never write the private key or API key to an artefact.
4. **Preserve a per-chain recovery path.** Persist each deployed guard's address and full manual migration instructions before submitting its proposal. The multichain deployment helper currently returns only after all chains finish; adapt its orchestration or add an incremental result hook so a later chain's deployment failure cannot hide earlier deployed guards. Save each chain's proposal status independently and report which chains are proposed or pending. If submission fails, leave its deployment record intact and exit non-zero after reporting the deployed guard and pending Safe migration. Add `--retry-guard-proposal` to the existing `lagoon-deploy-vault` command so it reads a deployment artefact and resubmits only missing or failed proposals without redeploying; use the existing `--chain-name` option to select one chain. It must recheck Safe, old and new guard addresses, on-chain nonce, owner, batch calldata and existing Service proposals. If chain state has changed, stop that chain and require operator inspection instead of posting stale calldata.
5. **Update operator output.** Show each chain's proposal hash and Safe URL, and state that the proposal has not been executed. Update `tradingstrategy-ai/docs/source/deployment/vault-deployment.rst` with automatic proposal behaviour, Safe owner review and execution, the retry option, and how deployment artefact submission status differs from the executor's later live `guard_migration` observation. Keep fresh vault deployments free of migration proposals.

## Verification

- Test old-guard, owner, batch-contract and API preflight before deployment; simulated deployments with no Transaction Service write; proposal success and artefact/URL output; identical-hash retry and conflicting pending nonce; and a submission failure followed by resubmission from the saved artefact. Include a multichain partial failure where the successful chain retains its recorded proposal and the failed chain remains recoverable.
- Add one Safe integration test on a local Anvil Safe, following the earlier `eth_defi.safe.tx.propose_safe_transaction()` and GMX AI MultiSendCallOnly proposal examples: deploy or reuse a Safe with an enabled old module, build the real signed batch, mock only the Transaction Service submission, execute the batch with Safe owner signatures, and verify the old module is disabled and the new module enabled. Keep the external Transaction Service out of CI.
- Run only the affected tests with `source .local-test.env` and the worktree first on `PYTHONPATH`. This worktree's `deps/` directories are empty, so use the parent repository's Poetry virtual environment and dependency source paths until they are restored here.
